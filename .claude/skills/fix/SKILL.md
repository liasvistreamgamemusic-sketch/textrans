# fix — 症状ではなく原因を直す

入力は症状 (エラー文・落ちるテスト・「〜のはずが〜になる」)。出力は **根本原因 1 行 + 根本箇所の修正 +
修正前に落ち修正後に通る回帰テスト + 同種箇所の掃討結果 + 再発防止**。品質の定義:

1. **修正を外すと別経路でも再現せず、修正後は不正な状態がシステム内に存在しない** (症状が「見えなくなった」のではない)
2. **別セッションの Claude が記録ファイルだけを読んで「なぜそこを直したか」を復唱できる**

このスキルは FABLE §3 (デバッグプロトコル)・04-loop §2・Iron Rule 1/5/8 を不具合修正の手順として実行する
ものであり、別の方法論を持ち込まない。基準は [references/root-cause-gate.md](references/root-cause-gate.md)。

## 絶対原則

1. **再現なしに修正しない。** 未再現なら「再現を得ること」がタスク。得られなければ `UNREPRODUCED` と
   必要な条件を記録に明記し、推測で直さない
2. **仮説なしに編集しない。** デバッグ中の全編集は記録ファイルの `H<n>:` に対応する。仮説の無い編集は
   推測であり、現場を壊して「なぜか直った」を生む
3. **修正は原因連鎖の「不変条件が最初に破られる箇所」に当てる** (root-cause-gate.md §3 の 3 つの判定テスト)。
   症状箇所への修正は応急処置であり、ユーザーの明示選択 + ラベル + 追跡なしには行わない (Iron Rule 5)
4. **二振り規則。** 同一仮説で 2 回修正に失敗したら編集を止め、仮説一覧の verified / assumed を見直して
   層を広げる (04-loop §2.5)
5. **テストを弱めない** (Iron Rule 1)。回帰テストは「修正前に、期待した理由で落ちる」のを見てから修正する
6. **症状が消えた ≠ 直った。** 報告には根本原因 1 行・修正箇所を選んだ根拠・同種箇所・再発防止を必ず書く

## 引数と Tier

- **引数**: 症状・エラー文・テスト名・チケット番号 (Redmine なら内容を取得)。無ければ直前の会話の失敗出力を入力にする
- **T0** (typo・自明な 1 行): 記録ファイル不要。返答に原因 1 行を書いて直す。hook に止められたら「T0 の自明な修正」と一言添えて続行
- **T1** (原因既知・1 ファイル・既存テストあり): 記録ファイルは最小 (SYMPTOM / ROOT_CAUSE_SITE / ROOT_CAUSE / 検証)。
  Phase 4 の質問は省略可 (推奨案 B を DECISION に書いて進む)
- **T2** (原因未知・複数層・flaky・再現が要る): 全 Phase
- **T3** (auth / 決済 / 移行 / 公開 API / データ破損): 全 Phase + code-reviewer・security-reviewer 系の独立レビュー。
  データ修復は別タスクとして分離する (Iron Rule 7)

## 全体フロー

```
Phase 0  Frame      症状 → 観察可能な AC。tier。NON-GOALS。記録ファイル作成
Phase 1  Reproduce  再現コマンドと実出力。flaky は回数で率を取る。未再現 → 条件再現 / UNREPRODUCED
Phase 2  Localize   出力全文 → レイヤ二分 / 時間二分 / 入力最小化 / 実データ出力。仮説台帳
Phase 3  Root-cause gate  原因連鎖 → ROOT_CAUSE_SITE 確定 → 候補修正をスメル照合 → 同種箇所 grep → WHY_NOT_CAUGHT
Phase 4  Branch     修正案 A/B/C を比較 → 本文に提示 → AskUserQuestion 1 回
Phase 5  Fix loop   回帰テスト red → 根本箇所で修正 → green → 同種箇所 → 計測コード除去 → lint / 型 / suite
Phase 6  Evidence   スメル一覧で diff を再走査 → (T2+) レビューエージェント → 報告
```

## Phase 0: Frame

- 症状を **AC** に言い換える: 「<失敗ケース> → <期待する結果>」+ 回帰ガード (周辺 suite が green のまま)。
  「ちゃんと動くようにする」は AC ではない。NON-GOALS に、ついでに直したくなるもの (リファクタ・隣の不具合) を書く
- XY 検査: 「X を直して」が手段で本当の目的が別にある (例: 「リトライを増やして」の目的はデータ欠損の解消) なら目的の方を AC にし、その旨を言う
- ユーザーの診断 (「原因は X」) は **仮説 H1** として台帳に入れる。検証なしに前提にしない (Iron Rule 10)
- 記録ファイル `<repo>/.fix/<slug>.md` を [references/fix-record-template.md](references/fix-record-template.md) で作る
  (`.git/info/exclude` に `.fix/` を追加)。以降の全 Phase はこのファイルを更新する — compaction 後はこれを読んで再開する

## Phase 1: Reproduce

- 修正前に失敗を自分で走らせ、**コマンドと実出力**を `REPRO:` に貼る。リポジトリの実際の検証コマンド
  (package scripts / Makefile / CI 設定) を使う — 発明しない
- ローカルで再現しない: 同じ入力の形・env・バージョンで**条件を再現**する (本番ログの入力をフィクスチャ化、同じ DB 状態を作る)。
  それでも再現しなければ `UNREPRODUCED (<試した条件>, <再現に必要なもの>)` と書き、ユーザーに必要なアクセス / データを求める
- flaky: 5〜10 回走らせて `FLAKY: n/m` を記録する。修正後に 0/m になっても**なぜ失敗していたか**を言えなければ直っていない (sleep で消えたなら隠しただけ)

## Phase 2: Localize — 理論の前に位置を特定する

- **出力を全部読む**: スタックトレース全体 (自分のコードの最初のフレーム)、エラーより前の warning、exit code、1 つ上のログ (supervisor / CI のジョブ全体)
- **レイヤ二分**: 入力 → パース → 変換 → 保存 → 出力の各段に既知の正しい入力を与え、最初に出力が狂う段を見つける
- **時間二分**: `git log --oneline -20 -- <対象>`。以前は動いていたなら `git bisect` か last-good / first-bad の diff 精読
- **入力最小化**: 何かを削ると通るまで失敗ケースを削る。最小ケースがバグを名指しする
- **実データを出力する**: 「流れているはずの値」ではなく境界の実際の値を print / log / REPL で見る
- **仮説台帳**: `H<n>: <仮説> → predicts → EXP → CONFIRMED | REFUTED` を記録に書いてから実験する。
  一時的な計測コード (print 等) はテストファイル・再現スクリプト・REPL で行うのを優先し、本体ソースに入れるときは
  `H<n>` に紐付けて Phase 5 で必ず除去する
- 広い探索 (全呼び出し元・同名パターンの全出現) は Explore 系エージェントに委譲する (読み取り専用・file:line 必須)。
  報告は inferred — 連鎖のリンクに使う事実は自分で読んで verified にする
- 二振り規則が発動したら: 編集停止 → 仮説一覧の各前提を verified / assumed に仕分け → assumed を検証 → 層を広げる
  (stale build・env / version 差・テスト自体の誤り・データが想定と違う・並行性・設定差・再現自体の誤り)

## Phase 3: Root-cause gate — ここを通るまで修正しない

[references/root-cause-gate.md](references/root-cause-gate.md) の規則で:

1. **原因連鎖**を書く (§1)。各リンクに根拠と事実タグ。assumed が残るなら Phase 2 に戻る
2. **根本原因**を「不変条件 X が Y で破られる」の 1 行で書き、その箇所を `ROOT_CAUSE_SITE: <path>:<line>` に確定する。
   この行が書かれるまで本体ソースを編集しない (Stop hook `root-cause-first-check.sh` が止める)
3. **候補修正をスメル照合** (§2 の 12 種)。当たるなら「なぜその箇所で直すのが正しいか」を連鎖で答える。答えられなければ候補を変える
4. **3 つの判定テスト** (§3: 別経路 / 多症状 / 状態消滅) で修正箇所を確認する
5. **同種箇所**を grep して `SIBLINGS:` に列挙する (§4)。無ければ検索したパターンを書いて「なし」
6. `WHY_NOT_CAUGHT:` を 1 行で書き、§5 の対応表から再発防止を 1 つ選ぶ

## Phase 4: Branch — 修正案の比較と 1 回の質問

修正案を 3 つ作る (strawman 禁止 — A も本物の選択肢として書く):

- **A 応急処置** (症状箇所): 最小 diff。残る不正状態・必要なラベル・追跡を明記
- **B 根本箇所** (ROOT_CAUSE_SITE): 影響範囲・必要なテスト。通常これが推奨
- **C 構造的** (このクラスの不具合を排除 — 型で不変条件を表現・入口で検証・API 形状の変更): コスト・別タスク化の要否

評価順序: 正しさ (AC 全充足・不正状態の消滅) > 単純さ > 可逆性 > 一貫性。`DECISION: B over A/C because …` を記録に書く。

**質問を出す直前に、原因連鎖・根本原因 1 行・3 案の比較・DECISION 案を本文に提示する** — preview だけに
載せない (表示されない環境がある)。内容が見えないまま選ばせない。AskUserQuestion は 1 回 (最大 3 問):

| # | 質問 | 選択肢 (先頭=推奨) |
| --- | --- | --- |
| 1 | 修正方針 | 「B 根本箇所で修正 (推奨)」 / 「C 構造的修正まで」 / 「A 応急処置 (根本原因は追跡)」 |
| 2 | 同種箇所 (SIBLINGS がある時のみ) | 「全て直す (推奨)」 / 「報告のみ (別タスク)」 |
| 3 | 再発防止 | 「回帰テストのみ (推奨)」 / 「+ 型・バリデーションで構造的に防ぐ」 |

T1 で推奨案が自明なら質問を省略し、DECISION を書いて進む。UNREPRODUCED のまま進む場合は質問 1 の
選択肢を「再現に必要なものを依頼して中断 (推奨)」/「A 応急処置」にする — 根本修正は再現なしに選べない。

**A が選ばれたとき** (root-cause-gate.md §6): 原因分析は省略しない。コード内に
`WORKAROUND(<参照>): <根本原因 1 行> — <撤去条件>` を置き、根本修正を追跡する先 (Redmine なら redmine-start で
チケット作成を提案) を決め、報告の先頭で「応急処置」と明記する。

## Phase 5: Fix loop — 小さく、毎回検証

1. **回帰テストを先に書く** (red): AC1 の失敗ケースをそのまま。走らせて落ちることと、**落ちた理由が期待通り**であることを
   確認して記録に書く (import error で落ちたのは red ではない)。ハーネスが無い領域は再現スクリプト / L4 の観察で代替し、報告に明記
2. **ROOT_CAUSE_SITE で修正する**。1 増分 = 1 関心事。NON-GOALS に書いたリファクタは混ぜない (気づいたら `LATER:` へ)
3. green を確認 → 周辺 suite を回す
4. **同種箇所**を 1 つずつ修正し、都度テスト (同一コミットでよい — 同じ根本原因の修正)
5. Phase 2 で入れた計測コード・一時ガードを**全て除去**する (`git diff` で確認)
6. lint (`--fix`) → 型 / build → suite の順で fail-fast に回す。グリーンでない状態で Phase 6 に進まない

修正中に想定外の挙動が出たら Phase 2 に戻る (推測で重ねない)。修正が 5 ファイル目に触れ始めたら tier が違う — 止めて再 Frame。

## Phase 6: Evidence — 敵対的セルフレビューと報告

1. `git diff` 全体を「対症療法として却下したいレビュアー」として読む。**スメル 12 種で再走査**し、当たる箇所ごとに
   連鎖上の根拠を言えるか確認する。ついでの変更・デバッグ残骸・テストの弱体化が無いか (05-evidence §4 の禁じ手)
2. T2+: code-reviewer 系エージェントに diff と記録ファイルを渡し「この修正が症状箇所のパッチである根拠を探せ」と指示する。
   T3: security-reviewer 系も並列。指摘は反証するか直す
3. AC を 1 項目ずつ照合する。未達は未達と書く
4. 報告 (日本語・結論から):
   - 1 行目: 直った / 応急処置 / 未解決 のどれか + 根本原因 1 行
   - 原因連鎖 (要約) / 修正箇所と、そこを選んだ根拠 (3 つの判定テストの答え)
   - 同種箇所: 直した・報告のみ・なし
   - 検証: 回帰テスト (修正前 FAIL の理由 / 修正後 PASS)・ladder の各段で実際に走らせたコマンドと結果。飛ばした段は理由付きで
   - 再発防止: 同梱したもの / LATER
   - OPEN: 未確認の前提・応急処置の追跡先
5. コミットはユーザーの指示があれば git-commit スキルで (`fix:` — 本文に根本原因を書く)。
   記録ファイル (`.fix/`) は残すか消すかを確認する

## してはいけないこと

- 再現せずに直す / 「おそらく X」のまま修正する
- エラーが出た行にガードを足して終わる (スメル #1) / 例外を握りつぶして既定値を返す (#2) / sleep・retry で競合を隠す (#3)
- テストの期待値・tolerance・skip で green にする (Iron Rule 1)
- ユーザーの「原因は X」を検証せずに X を直す (Iron Rule 10)
- 同一仮説で 3 回目の修正を試す (二振り規則)
- ROOT_CAUSE_SITE を書く前に本体ソースを編集する / 形だけ書いて通す (hook は形しか見ない — 中身の責任はここ)
- 応急処置を自分の判断で選ぶ / ラベルと追跡なしに置く
- 同種箇所を探さずに 1 箇所だけ直す / 計測用の print・一時ガードを残す
- 「テストが通った」を観察せずに報告する (Iron Rule 2)
