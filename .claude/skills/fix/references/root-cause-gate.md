# 根本原因ゲート — 原因連鎖・対症療法スメル・修正箇所の規則

Phase 3 (Root-cause gate) と Phase 6 (セルフレビュー) の基準。「症状が消えた」と「直った」を
機械的に区別するための道具。SKILL.md の絶対原則 3 (修正は不変条件が最初に破られる箇所に当てる) を
この文書の規則で判定する。

## 1. 原因連鎖 (causal chain) の書式

症状から根本原因まで、**観察した事実だけ**でリンクをつなぐ。各リンクに根拠 (file:line / 実出力 / 実験結果) と
事実タグ (verified = このセッションで観察 / inferred = 強い間接証拠) を付ける。assumed のリンクが残る連鎖は
未完成 — 実験で verified に昇格させるか、連鎖を短く切り直す。

```text
症状        : POST /reports が 500 (実出力: `KeyError: 'tenant_id'` at report_service.py:88)        [verified]
← 直接原因  : report_service.build() が payload["tenant_id"] を読むが payload に無い (print 実測)       [verified]
← 中間原因  : api/reports.py:41 が ReportIn → dict 変換で exclude_unset=True を渡している               [verified, api/reports.py:41]
← 根本原因  : ReportIn.tenant_id が Optional で既定 None — 「tenant_id は常に存在する」という不変条件が
              スキーマで表現されていない (schemas/report.py:17)。exclude_unset はそれを露出させただけ        [verified, schemas/report.py:17]
```

根本原因の定義: **それより上流に、同じ不具合を生む原因が存在しない箇所**。「不変条件 X が Y で破られる」の
形で 1 行に書けなければ、まだ根本に届いていない (「たまたま None だった」は原因ではなく症状)。

連鎖を伸ばす問い: 「この値はなぜこうなったか?」「それを保証すべきなのは誰 (どの層) か?」
「同じ保証が無い他の入口は?」— 答えが「設計上そうなっている」「外部仕様」に達したら止める
(その先は NON-GOAL か構造的修正案 C の材料)。

## 2. 対症療法スメル 12 種

候補の修正がこの一覧に当たるなら、**原因連鎖の中で「なぜその箇所で直すのが正しいか」を答えられない限り採用しない**。
当たる = 即不採用ではない (null ガードが本当に正しい境界であることもある)。問われるのは根拠の有無。

| # | スメル | 典型形 | 隠しているもの |
| --- | --- | --- | --- |
| 1 | 症状箇所のガード追加 | `if x is None: return` / `?.` / `if not items: continue` | なぜ None / 空が来るのか |
| 2 | 握りつぶし・既定値フォールバック | `try: … except: return default` / `catch {}` / `.get(k, 0)` | 失敗そのもの (Iron Rule 8) |
| 3 | retry・sleep・タイムアウト延長 | `time.sleep(1)` / `retries=5` / `timeout=120` | 競合・順序依存・遅い本当の理由 |
| 4 | 型を黙らせる | `as any` / `# type: ignore` / `str(x)` / `int(x or 0)` / `cast()` | 境界での型不整合 |
| 5 | 特定値の特別扱い | `if id == 42` / `if name in ("legacy", …)` / テスト入力に合わせた分岐 | 一般則の欠落 |
| 6 | caller 側での補正 | callee の不正な戻り値を呼び出し元で整形・除去 | callee の契約違反 |
| 7 | 設定値・閾値で消す | 上限を上げる・バッチを小さくする・制限を緩める | 上限に当たる理由 (リーク・N+1) |
| 8 | テスト側の変更 | 期待値変更・`skip`・tolerance 拡大・`assertIn` 化 | 挙動の誤り (Iron Rule 1) |
| 9 | 同じパッチのコピペ | 複数箇所に同一ガードを配る | 共通の上流原因 (1 箇所で直せる) |
| 10 | 順序入替・再初期化・キャッシュクリアで「なぜか直る」 | import 順を変える・`reset()` を足す・`rm -rf cache` | 隠れた状態依存 |
| 11 | データだけ直す | DB の該当行を手で直す・ファイルを置き換える | それを生んだコード経路 |
| 12 | 依存のピン留め・ダウングレード | `lib==1.2.3` に固定して回避 | 互換性の根本原因 (呼び出し側の誤用か上流バグか) |

## 3. 修正箇所の規則 — 3 つの判定テスト

修正は原因連鎖の**不変条件が最初に破られる箇所**に当てる。候補箇所に対して 3 問とも答える:

1. **別経路テスト** — この修正を外して、別の入口・別の入力から同じ原因を踏んだら再現するか?
   → 再現する = 症状箇所。もっと上流にある
2. **多症状テスト** — 同じ根本原因で説明できる他の症状 (別のエラー・別の画面の不具合・過去の issue) があるか?
   → ある = 根本に近い。その症状も修正後に消えるはず (検証に使う)
3. **状態消滅テスト** — 修正後、不正な状態 (None の tenant_id・負の残高・未検証の入力) はシステム内に
   **存在しなくなる**か、**存在するが見えなくなる**だけか?
   → 見えなくなるだけ = 対症療法

3 問を通った箇所が `ROOT_CAUSE_SITE:`。通らないが採用する場合は応急処置 (§6) として扱う。

## 4. 同種箇所の掃討 (siblings)

根本原因を「パターン」に言い換えて grep する — 同じ API の同じ誤用、同じ型の暗黙変換、同じ境界の未検証、
同じ util の同じ呼び方。例:

```bash
grep -rn "exclude_unset=True" app/api/            # 同じ変換を他の入口も使っていないか
grep -rn "Optional\[.*tenant_id" app/schemas/     # 同じ不変条件の欠落
```

結果は記録の `SIBLINGS:` に file:line で列挙する (無ければ検索したパターンを書いて「なし」)。
修正するか報告のみかは Phase 4 の質問で決める — 同種箇所の修正は同じ根本原因の修正なので
同一コミットに入れてよいが、1 箇所ずつテストを通して進める。

## 5. WHY_NOT_CAUGHT → 再発防止の対応表

「なぜ今まで検出されなかったか」を 1 行で書き、対応する防止策を 1 つ選ぶ。
1 増分 (同じ修正の中) で収まるものだけ実施し、それ以上は `OPEN:` / `LATER:` に回して報告する。

| なぜ検出されなかったか | 再発防止 (修正に同梱する最小単位) |
| --- | --- |
| その経路のテストが無い | 回帰テスト (修正前に落ち・修正後に通る) — **常に必須** |
| 型が緩い (Optional / any / dict) | 型を狭める (必須フィールド化・Literal・TypedDict・Enum) |
| 境界 (入口) で検証していない | 入口 1 箇所でバリデーション (スキーマ / パーサ) し、内部は信頼する |
| 不変条件が暗黙 (コメントにも無い) | 型・コンストラクタ・assert で表現する |
| エラーパスが無音 | ログ (Iron Rule 8) — 握りつぶし箇所にログを足す |
| 環境差 (本番だけ・特定 OS だけ) | 設定値インベントリと環境定義の突合 (code-quality.md の env 規則) |

## 6. 応急処置 (ワークアラウンド) ポリシー — Iron Rule 5

**省略できるのは「修正箇所」だけで、原因分析 (再現・連鎖・ROOT_CAUSE_SITE) は省略できない。**
根本原因が特定できない (UNREPRODUCED / 外部依存のバグ) 場合も、分かった所までの連鎖と
「特定できていない」ことを記録してから応急処置に進む。

許可条件 (全て):

- ユーザーが Phase 4 の質問で「応急処置」を**明示選択**した (Claude の判断では選ばない)
- 根本修正が今できない理由が記録の `DECISION:` にある (別リリース・外部ライブラリの修正待ち・データ移行が必要 等)
- コード内に撤去条件付きラベルがある:
  `# WORKAROUND(<チケット or 参照>): <根本原因 1 行> — <撤去条件 (例: lib 2.0 で修正済み / #1234 で根本修正)>`
- 追跡先がある (Redmine が使える環境なら redmine-start でチケット作成を提案。無ければ OPEN に残し報告で指名)
- 報告の先頭行に「応急処置」と明記し、根本修正に必要な作業を書く

応急処置でもテストは書く — ただし「応急処置が効いている」テストではなく、**根本原因が直ったら
通るべき挙動**のテストを `xfail` / `skip` (チケット参照付き) で置き、撤去時に有効化する。
